## 1. Что это

РЕЗЕРВ — B2B-площадка закупок, например металлопроката. На ней работают две роли:

- **Поставщик** выкладывает каталог с ценами и остатками, получает заказы, торгуется, отгружает и доставляет.
- **Покупатель** ведёт склад, видит прогноз дефицита, находит поставщиков, заказывает, торгуется и считает экономию.

За обе стороны могут торговаться **ИИ-агенты на Google Gemini**, каждый в рамках правил своего кабинета.

Всё происходит на сайте. Интеграций с 1С и другими системами в прототипе нет.

## 2. Технологии

| Слой | Что используется |
|---|---|
| Фронтенд | Статический HTML + React 18 (UMD, без сборки). Страницы собраны в Claude Design, у них свой шаблонизатор (`dc-runtime.js`) |
| База и API | **Supabase**: PostgreSQL + автоматический REST (PostgREST) + Auth |
| Логика в базе | SQL-функции (RPC) с `SECURITY DEFINER`, триггеры, Row Level Security |
| Поиск похожих товаров | Расширение PostgreSQL **pg_trgm** (сходство строк по триграммам) |
| ИИ | **Google Gemini API**, модель по умолчанию `gemini-2.5-flash` |
| Серверный код ИИ | **Supabase Edge Functions** (Deno, TypeScript): `seller-agent`, `buyer-agent` |
| Вызовы из базы | Расширение **pg_net** (HTTP-запросы из триггеров) |
| Хранение ключей | **Supabase Vault** (шифрование) |
| Excel | **SheetJS** 0.20.3: импорт прайса и остатков, выгрузка отчёта |
| Почта | Supabase Auth + свой SMTP (Яндекс), свои HTML-шаблоны писем |
| Хостинг | **Vercel** (статика из папки `site`), автодеплой из GitHub |
| Локальный запуск | `server.js` на Node.js (без зависимостей) |

## 3. Архитектура

```
 Браузер (site/*.html)
   │  supabase-js: вход, чтение таблиц, вызов RPC
   ▼
 Supabase
   ├─ Auth ─────────────── вход по email/паролю, письма через SMTP Яндекса
   ├─ PostgreSQL
   │    ├─ таблицы + RLS ── кто что видит (владелец кабинета и его команда)
   │    ├─ RPC-функции ──── все изменения заказов, склада, импорт и т. д.
   │    └─ триггеры ─────── уведомления, приход на склад, вызов ИИ (pg_net)
   ├─ Vault ────────────── зашифрованные ключи Gemini кабинетов
   └─ Edge Functions
        ├─ seller-agent ─── ИИ поставщика ──┐
        └─ buyer-agent ──── ИИ покупателя ──┴──► Google Gemini API
```

**Главный принцип:** браузеру ничего не доверяется. Права проверяет база (RLS и проверки внутри функций), поэтому подделать запрос с сайта бесполезно. Ключ Gemini и сервисный ключ Supabase есть только у Edge Functions.

### Как устроен кабинет

`cabinet.html` — это одна страница: разметка с шаблонами плюс класс `Component`.

- Все данные хранятся в `state`.
- Метод `renderVals()` каждый раз собирает плоский объект значений для шаблона. Это отдельные функции на каждый раздел: `stVals` (склад), `odVals` (заказы), `histVals` (история), `agVals` / `baVals` (правила агентов) и т. д.
- Шаблон рисует `{{ значения }}`, `<sc-if>` и `<sc-for>`.
- **Наблюдатель в команде** не может ничего изменить: обработчики из списка `RO_BLOCK` подменяются на сообщение «только просмотр» (функция `guardReadOnly`).
- **Устаревшие ответы:** у каждой загрузки свой счётчик запросов (`this.xxReq`). Если пользователь быстро переключил кабинет, опоздавший ответ отбрасывается.
- **Обновление:** раз в 10 секунд (`odTick`) подтягиваются уведомления, а на страницах заказов и сами заказы.

## 5. Вход, роли и команды

### Регистрация и вход
- **Способ входа:** email и пароль через Supabase Auth. Письма подтверждения и сброса пароля приходят через SMTP Яндекса в своём оформлении.
- **Роль** (покупатель `buy` или поставщик `sell`) выбирается при регистрации, передаётся в метаданных пользователя и записывается в таблицу `profiles` триггером `handle_new_user`. Поменять роль из кабинета нельзя.
- **Ссылка-приглашение поставщика** `…/cabinet.html#signup-sell` открывает регистрацию с уже выбранной ролью «Поставщик».
- **Другие вкладки:** если в другой вкладке выйти из аккаунта или войти в другой, кабинет это замечает (`onSessionChange`) и возвращает на вход или перезагружается.

### Реквизиты компании
- **Поля:** название, ИНН, КПП, ОГРН/ОГРНИП, юр. адрес, склад, телефон, категории.
- **Проверка:** только формат (цифры и длина), контрольные суммы ИНН и ОГРН не проверяются.
- **Кто может менять:** владелец и менеджеры команды, через функцию `update_team_company`.

### Команды
- **Команда — это кабинет владельца.** Участники работают в нём по доступу:
  - **Наблюдатель** (`viewer`) — только смотрит;
  - **Менеджер** (`editor`) — работает с заказами, складом, правилами и реквизитами.
- **Приглашение** — одноразовая ссылка на 7 дней (`team_invites`). Её принимает функция `accept_invite`.
- **Управлять командой** (приглашать, менять доступ и должность, удалять) может только владелец.
- **Переключатель кабинетов:** у каждого есть свой кабинет и кабинеты команд, где он участник. Роль (покупатель/поставщик) берётся от владельца открытого кабинета.
- **Проверка прав в базе:** функции `is_team_member`, `is_team_editor`, `can_view_party(owner)`, `can_act_party(owner)`.

### Как защищены данные
- **RLS включён на всех таблицах.** Читать можно своё и данные кабинетов, где ты в команде. Видимые позиции каталога и отзывы видят все вошедшие пользователи.
- **Права на уровне колонок:** например, остаток на складе нельзя поменять прямым `update`, только через функцию движения. Так у каждой цифры есть история.
- **Изменения идут через функции.** Все изменения заказов, склада, импорта и команд делают функции с `SECURITY DEFINER` и `set search_path = ''`. Каждая сама проверяет права.

## 7. Каталог и прайс (поставщик)

- **Позиция каталога:** название, стандарт (ГОСТ/ТУ), единица, цена за единицу, остаток и «видна покупателям».
- **Добавление:** позиции добавляются по одной на сайте или загрузкой Excel/CSV. Для этого есть шаблон и инструкция прямо на странице.
- **Разбор файла** (`price-import.js`):
  - колонки находятся по заголовкам, порядок не важен. Например, «Наименование / Товар / Позиция», «Цена / Стоимость», «Остаток / Наличие / Кол-во», «Ед. изм.», «ГОСТ / Стандарт», «Видна»;
  - CSV читается в UTF-8, а если текст не распознался — в windows-1251;
  - номера строк в ошибках совпадают с номерами в Excel.
- **Загрузка в базу:** одним запросом `import_catalog`. Позиция ищется по «название + стандарт» без учёта регистра: если нашлась — обновляется, если нет — добавляется.
- **Резерв под заказ:** когда цена по заказу согласована, количество списывается с остатка каталога. При отмене подтверждённого заказа оно возвращается.

## 8. Поставщики и рейтинг

### Кого видит покупатель
В списке только поставщики, у которых есть хотя бы одна **видимая позиция в наличии**. Заблокированных можно скрыть, белый список отмечается переключателем. Отметки общие для всей команды покупателя.

По клику открывается карточка поставщика: реквизиты, последние отзывы и каталог с кнопкой «Заказать» у каждой позиции.

### Как считается рейтинг (`get_supplier_rating`)
| Показатель | Формула |
|---|---|
| Индекс надёжности | средняя оценка всех отзывов, округлённая до 0,1 |
| Вовремя | доля «в срок» среди **последних 20** отзывов, где это оценено |
| Качество | доля «без замечаний» среди последних 20 оценённых |
| Рекламации | отзывы с «качество с замечаниями» за 6 месяцев |
| Место | «входит в топ N%» — только если поставщиков с отзывами не меньше 5: `N = ⌈100 × (1 + число поставщиков с оценкой выше) / всего поставщиков с отзывами⌉` |

## 9. Заказы и переговоры

### Статусы
```
negotiation ──► confirmed ──► shipped ──► arrived ──► delivered
 переговоры     согласован    отгружен    доставлен    получен (закрыт)
     │                │
     ├─► rejected     └─► cancelled (покупатель отменил до отгрузки)
     └─► cancelled
```
- **Кто что отмечает:** «отгружен» и «доставлен до пункта» отмечает поставщик, «получен» — только покупатель.
- **Как идёт торг:** стороны ходят по очереди, поле `turn` показывает, чей ход. На своём ходе можно принять цену другой стороны или предложить свою.
- **Кто начинает:** заказ создаётся с ценой покупателя, первый ход у поставщика.
- **Проверки:** каждое действие проходит через `order_action`. Функция проверяет права стороны, статус и очередь хода, пишет системное сообщение в переписку и меняет статус.
- **Склад:** при получении заказа (`delivered`) триггер пополняет подходящую позицию склада покупателя. Сначала ищется точное совпадение названия, потом похожее (как в сравнении цен).

### Страницы
- **Поставщик:** «Переговоры», «Заказы».
- **Покупатель:** «Заказы поставщикам», «Проекты заказов».

Это одно рабочее место с вкладками «В переговорах / В работе / Закрытые / Все», полосой этапов и перепиской.

## 10. Сравнение цен с рынком

**Похожие позиции** у разных поставщиков ищет функция `market_match`. Позиции считаются похожими, если:
- у них **одинаковая единица измерения**, и
- **сходство названий** (pg_trgm `similarity`) не меньше **0,5**, или совпадает стандарт (ГОСТ/ТУ) и сходство названий не меньше **0,3**.

Что строится на этом:
- **У поставщика «Сравнение цен»** — по каждой его позиции: сколько похожих предложений на рынке, минимальная, средняя и максимальная цена, сколько конкурентов дешевле, суммарный остаток рынка. По клику открываются все предложения с рейтингами.
- **Агенты** используют те же данные о рынке как аргумент в торге.

## 11. Склад и прогноз (покупатель)

### Данные
- **Позиция:** название, артикул, единица, остаток, срок поставки (дни), страховой запас (дни), целевой запас, режим расхода (авто или вручную), «на контроле».
- **Остаток** меняется только **движениями**: приход, расход, инвентаризация. Каждое движение пишется в журнал с «было → стало».
- **Остатки из Excel** загружаются через `import_stock`. Позиция ищется по артикулу, потом по названию. Изменение остатка записывается как инвентаризация «Загрузка из Excel: файл».

### Формулы (`stockCalc` в `cabinet.html`)

| Величина | Как считается |
|---|---|
| **Расход в день (авто)** | сумма списаний за последние 30 дней ÷ число дней (от 1 до 30, не больше «возраста» позиции). Если списаний нет, берётся ручное значение |
| **Расход в день (вручную)** | значение из настроек позиции |
| **Хватит на, дней** | остаток ÷ расход |
| **Точка заказа (ROP)** | расход × (срок поставки + страховой запас) |
| **Целевой запас** | заданный вручную или, если не задан, расход × (срок поставки + страховой запас + 30) |
| **Сколько заказать** | ⌈целевой запас − остаток − уже в пути⌉ |

**Статус позиции:**
- **КРИТИЧНО** — дней запаса не больше срока поставки: заказ не успеет прийти;
- **СКОРО ЗАКАЗ** — дней запаса не больше «срок + страховой запас + 2»;
- **НОРМА** — во всех остальных случаях;
- **НЕТ РАСХОДА** — расход неизвестен;
- **В ЗАКАЗЕ** — по позиции есть открытый заказ.

**Заказы в пути.** Открытые заказы находятся по названию: после нормализации оно совпадает с названием позиции или входит в него (при длине от 4 символов). День поставки считается так:
- «доставлен» — поступает сегодня;
- «отгружен» — через половину срока поставки (или раньше, если такая дата указана в заказе);
- «согласован» — к дате «поставить до» или через срок поставки.

### График «прогноз на 30 дней»
Модель идёт по дням:
1. Каждый день остаток уменьшается на расход (но не ниже нуля).
2. В день поставки добавляется количество из заказа.
3. Если позиция на контроле и остаток опустился до точки заказа, а поставок впереди нет, модель «оформляет» условный заказ. Он придёт через срок поставки в объёме «целевой запас − остаток».

Цвета столбиков:
- **белый** — день поставки;
- **оранжевый** — ниже точки заказа или ноль;
- **зелёный** — норма.

Пунктир — точка заказа.

**Рекомендация под графиком** собирается из этих чисел. Например: «Остатка хватит на 5 дн., а поставка занимает 7 дн. — заказывайте сейчас: около 40 т».

**Кнопка «✦ Прогноз ИИ-агента»** дополнительно отправляет историю в Gemini. Формулы кабинета при этом не меняются (см. раздел 16).

## 12. История и экономия (покупатель)

- **Сделка** — заказ в статусе «согласован», «отгружен», «доставлен» или «получен».
- **Экономия по заказу** = (цена прайса на момент заказа − согласованная цена) × количество.
- **Снижение к прайсу, %** = экономия ÷ сумма по ценам прайса.
- **Карточки сверху** за 12 месяцев или за всё время: экономия, сколько согласовано (получено / в работе), среднее снижение цены, сумма закупок и число поставщиков.
- **График** — 12 столбиков по месяцам **по дате согласования**. Переключатель «Экономия / Закупки», значения в тысячах рублей, текущий месяц выделен.
- **Таблица** всех заказов с фильтрами по периоду, статусу и поиску.
- **Выгрузка в Excel** (SheetJS), 4 листа:
  - «Сводка» — компания, период, итоги;
  - «Заказы» — с учётом фильтров, с датами, суммами, экономией и автофильтром;
  - «По месяцам»;
  - «По поставщикам».

  Числа в файле настоящие, с денежным, процентным и датовым форматом, а не текстом.

## 13. Главные страницы («Обзор»)

**Покупатель:**
- **Подзаголовок:** «N дел ждут вашего решения» или «Всё под контролем».
- **Карточки:**
  - «Ждут вашего решения»;
  - «Экономия в <месяц>» — сделки, согласованные в этом месяце;
  - «Позиций на контроле» (сколько критично);
  - «Заказов в работе» (сколько в пути и на какую сумму).
- **«Ждут вашего решения»** — реальные дела по срочности:
  - **ПРИЁМКА** — поставщик доставил, нужно подтвердить получение;
  - **ВАШ ХОД** — поставщик предложил цену;
  - **ДЕФИЦИТ** — критичная позиция без заказа;
  - **ОТЗЫВ** — полученный заказ без оценки.
- **«Последние события»** — последние уведомления, по клику открывается заказ.
- **«Ближайшие к точке заказа»** — позиции склада с наименьшим запасом.

**Поставщик:**
- **Карточки:** «Ваш ход в переговорах», «Заказов в работе» (сколько отгрузить), «Продажи за месяц» (сумма согласованных в этом месяце), «Рейтинг».
- **Списки:** что отгрузить или довезти, где покупатели ждут ответа.

## 14. Уведомления

- **Кто создаёт:** только **триггеры в базе**. Сайт уведомления не создаёт, поэтому их нельзя подделать.
- **Кому:** адресат — кабинет. Уведомления видит владелец и вся его команда. Отметка «прочитано» у каждого пользователя своя (`notification_seen`).
- **Виды:**
  - новый заказ;
  - встречное предложение;
  - сообщение;
  - цена согласована;
  - отказ, отмена;
  - отгружен, доставлен, получен;
  - новый отзыв.
- **Какие показывать** — личная настройка каждого в «Настройках» (`notify_prefs`).
- **Где видно:** колокольчик со счётчиком и лента «Последние события» на главной.
- **Обновление:** раз в 10 секунд.
- **Формат чисел** в тексте: «54 500 ₽/т» (функция `fmt_qty`: разряды через неразрывный пробел, дробная часть через запятую).

## 15. Отзывы

- **Когда можно оставить:** только по своему заказу в статусе «получен» и один раз на заказ (`review_create`).
- **Что в отзыве:** звёзды 1–5, «пришло в срок?», «качество без замечаний?», комментарий.
- **Что происходит дальше:** отзыв сразу учитывается в рейтинге, поставщик получает уведомление.

## 16. ИИ-агенты (Gemini)

### Как устроено
```
Покупатель предложил цену ─► orders.turn = 'supplier'
   └─► триггер orders_agent_hook (если у поставщика включён автоответ)
         └─► pg_net: POST /functions/v1/seller-agent {action:'auto', order_id}
               ├─ agent_context(order)  → заказ, правила, переписка, склад, рынок, история
               ├─ Gemini (JSON-ответ по схеме)
               ├─ жёсткие границы в коде функции
               └─ order_agent_action   → база ещё раз проверяет границы и записывает ответ
Поставщик ответил ─► orders.turn = 'buyer' ─► то же самое для buyer-agent
```
Ответ агента появляется через 3–6 секунд, а у второй стороны — после ближайшего обновления страницы (раз в 10 с). Если автоответ включён у обеих сторон, агенты торгуются друг с другом, пока одна не примет цену или не закончатся раунды.

### Агент поставщика (`seller-agent`)
- **Правила** (раздел «ИИ-агент»):
  - максимальная скидка от прайса;
  - доп. скидка за объём и объём, с которого она действует;
  - число раундов;
  - тон (деловой, дружелюбный, кратко);
  - свои указания текстом.
- **Минимальная цена** = прайс × (1 − (макс. скидка + доп. скидка, если объём достигнут) ÷ 100).
- **Что видит агент:**
  - переписку;
  - прайс и остаток позиции;
  - минимальную цену (с запретом называть её покупателю);
  - цены других поставщиков;
  - историю сделок с этим покупателем;
  - номер раунда.
- **Границы в коде:**
  - цена не ниже минимальной;
  - не выше прайса;
  - не выше прошлого своего предложения;
  - если встречная выходит не выше цены покупателя — просто принять;
  - в автоответе отказывать нельзя.
- **Когда передаёт заказ человеку:**
  - заказано больше остатка;
  - раунды закончились;
  - дневной лимит 300 ответов исчерпан.

### Агент покупателя (`buyer-agent`)
- **Правила** (раздел «Правила агента»):
  - целевая скидка — к ней стремиться;
  - минимальная скидка — дороже не соглашаться;
  - раунды, тон, указания.
- **Цели и границы:**
  - **цель** = прайс × (1 − целевая скидка ÷ 100);
  - **потолок** = прайс × (1 − минимальная скидка ÷ 100).
- **Что видит агент:**
  - переписку;
  - цель и потолок;
  - рынок;
  - рейтинг поставщика и долю поставок вовремя;
  - историю сделок;
  - **свой склад**: остаток, расход, на сколько дней хватит, срок поставки. Если склад заканчивается, агент соглашается быстрее.
- **Границы в коде:**
  - не дороже потолка;
  - не ниже своего прошлого предложения;
  - если поставщик согласился на нашу цену — принять;
  - раунды кончились, а цена не выше потолка — принять;
  - выше потолка — передать человеку.
- **Прогноз по складу** («✦ Прогноз ИИ-агента»). Агент получает:
  - остаток и параметры позиции;
  - расчёт формул кабинета;
  - списания и приходы по дням за 90 дней;
  - заказы в пути;
  - до 8 самых дешёвых предложений поставщиков.

  В ответ он даёт: риск дефицита, короткий вывод, когда и сколько заказать, у кого выгоднее, до 4 советов.

### Подсказка вместо автоответа
Кнопка «✦ Подсказка ИИ» есть на своём ходе в переговорах у обеих сторон. Она показывает решение, цену, текст сообщения и объяснение. Дальше можно отправить как есть или поправить перед отправкой. Работает и при выключенном автоответе.

### Двойная защита от ошибок модели
1. **Код функции** приводит ответ Gemini к границам правил. Если решение поменялось (модель написала «принимаем», а цена выше потолка), текст заменяется на шаблонный, чтобы сообщение не противоречило цене.
2. **Сама база** в `order_agent_action` / `order_buyer_agent_action` ещё раз проверяет минимальную цену или потолок, статус и очередь хода. Даже при ошибке в коде невыгодная сделка не пройдёт.

### Ключи и модели
- **Порядок выбора ключа:**
  1. **свой ключ кабинета** (Настройки → «ИИ · Свой ключ Gemini»);
  2. **ключ платформы**: `GEMINI_API_KEY` для поставщиков, `GEMINI_API_KEY_BUYER` для покупателей. Нагрузка разделена между двумя ключами.
- **Если свой ключ сломался** (недействителен, кончились лимиты), кабинет показывает причину, а агент продолжает работать на ключе платформы.
- **Хранение своего ключа:**
  - перед сохранением ключ проверяется запросом к Google (без траты квоты);
  - хранится в **Supabase Vault** в зашифрованном виде;
  - на сайте видны только последние 4 символа;
  - расшифровать может только Edge Function.
- **Модель выбирается** в карточке ключа (2.5 Flash, 2.5 Flash-Lite, 3.5 Flash-Lite, 3.5 Flash, 2.5 Pro).
- **Если модель перегружена** (ответ 503/429), функция пробует следующую: `gemini-2.5-flash` → `gemini-3.5-flash-lite` → `gemini-2.5-flash-lite`.
- **Параметры запроса:** `temperature 0.4`, ответ строго в JSON по схеме (`responseSchema`).

## 17. Безопасность

- **Anon-ключ Supabase** в `config.js` публичный. Сам по себе он ничего не даёт: доступ ограничивают RLS и проверки в функциях.
- **Ключи, которых нет ни на сайте, ни в репозитории:**
  - сервисный ключ Supabase — только в Edge Functions;
  - ключи Gemini — в секретах функций или в Vault.
- **Функции, которые могут вызвать только Edge Functions** (роль `service_role`): действия агентов, чтение и запись ключей.
- **Триггеры вызывают функции агентов с anon-ключом.** Функция сама проверяет, что автоответ включён, сейчас ход этой стороны и лимиты не исчерпаны. Поэтому лишний вызов ничего не сломает.
- **Все функции `SECURITY DEFINER`** имеют `set search_path = ''`: подмена функций через схему невозможна.
- **Команды:** наблюдатель физически не может ничего изменить, база не даст.

## 18. Хостинг и обновление

- **GitHub:** `alek10er/Rezerv`, ветка `main`.
- **Vercel:** публикуется папка `site`, без установки пакетов и сборки (`vercel.json`). Каждый `git push` в `main` публикуется автоматически.
- **Supabase Auth → URL Configuration:** Site URL = адрес Vercel, в Redirect URLs — `https://rezerv-srpq.vercel.app/**` и `http://localhost:3000/**`. От этого зависят ссылки в письмах.
- **Изменения в базе и функциях не публикуются через GitHub.** SQL выполняется вручную в SQL Editor, код Edge Functions вставляется в редактор функции в Supabase Dashboard.
- **Локально:** `npm start` → http://localhost:3000.

## 19. Что в прототипе пока не сделано

- **Интеграции** (1С, ЭДО, внешние площадки) — в настройках помечены «Недоступно во время тестирования».
- **Уведомления на почту и в Telegram** — сейчас только на сайте.
- **Мгновенное обновление:** страницы обновляются раз в 10 секунд, Supabase Realtime не подключён.
- **Автоматическое создание заказов агентом** при достижении точки заказа — агент пока только советует.
- **Скорость ответа поставщика и отказы после согласования** в рейтинге — в функции рейтинга есть заготовки полей, на странице «Рейтинг» они не показываются.
- **Защиты от спама при регистрации** (капча) нет, есть только встроенные лимиты Supabase.
